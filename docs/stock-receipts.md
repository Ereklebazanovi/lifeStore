# მიღება და საწყობის გაერთიანება

> სტატუსი: სპეციფიკაცია, 2026-11-22. ოთართან შეთანხმებულია ჩატში (22.11). კოდი ჯერ არ დაწერილა.

## რატომ

- ტვირთის შეყვანა ახლა თითო პროდუქტზე „+“-ით ხდება. სისტემაში არ ჩანს, ვისგან რა და როდის მოვიდა.
- ბრუნვითი უწყისის „მიღება“ ყველა მატებას ითვლის. 22.08–22.11-ის 198 ცალიდან რეალური შევსება მხოლოდ 91 ცალი იყო, დანარჩენი შეკვეთებიდან დაბრუნებული საქონელია. „გაყიდვაში“ კი დაზიანებული საქონლის ჩამოწერაც ხვდება.
- „პროდუქტები“ და „საწყობი“ ერთი და იგივე სიაა, მხოლოდ ღილაკებია ორ გვერდზე გაფანტული.

## შედეგი ერთი შეხედვით

- მენიუ: „პროდუქტები“ ქრება, რჩება **საწყობი**, ემატება **მიღება** (საწყობის შემდეგ). მაღაზია უცვლელია.
- ტვირთი ერთ ჩანაწერად შედის: თარიღი, მომწოდებელი, პროდუქტები. საჭიროების შემთხვევაში ნაწილი იქვე იგზავნება მაღაზიაში.
- ახალი პროდუქტი **მხოლოდ მიღებიდან** იქმნება, დამალული. ფოტოს, ფასსა და აღწერას ოთარი საწყობში ✏️-ით ამატებს და მერე რთავს.
- მარაგი მხოლოდ ოთხი გზით იცვლება: **მიღება**, **კორექცია**, **შეკვეთები**, **მაღაზია**. პროდუქტის ფორმა მარაგს აღარ ცვლის.
- ბრუნვით უწყისში თითო მოძრაობას თავისი სვეტი აქვს.

### ფორმა „ახალი მიღება“

| ველი | წესი |
|---|---|
| თარიღი | ნაგულისხმევად დღევანდელი; წარსული დღე შეიძლება, მომავალი არა |
| მომწოდებელი | სავალდებულო, თავისუფალი ტექსტი (≤200). ჩაწერისას სისტემა სთავაზობს ადრე გამოყენებულ სახელებს. ცალკე სია არ არსებობს |
| დოკუმენტის № | არასავალდებულო: ზედნადები, ინვოისი, დეკლარაცია |
| კომენტარი | არასავალდებულო (≤2000) |
| ხაზები | 1–200; ერთი პროდუქტი ერთხელ (გამეორებული ხაზები ჯამდება) |

**ხაზი:** პროდუქტი, რაოდენობა (მთელი, ≥1) და „აქედან მაღაზიაში“ (0..რაოდენობა, ნაგულისხმევად ცარიელი). გვერდით ჩანს „საწყობში ახლა“ და „შენახვის შემდეგ“.

**ძებნა და კლავიატურა** მუშაობს ისე, როგორც მაღაზიის ფორმაში: სახელით ან კოდით, ↑/↓, Enter ამატებს. სიაში დამალული პროდუქტებიც ჩანს, ნიშნით.

**ახალი პროდუქტი:** თუ ძებნამ ვერაფერი იპოვა, ჩნდება „+ ახალი პროდუქტი“ ღილაკი.
- **სახელი:** სავალდებულო.
- **კოდი:** სავალდებულო. იგივე წესით, რაც დღეს: `A-Z 0-9 -`, დიდი ასოები, უნიკალური ყველა პროდუქტსა და ამავე ფორმის სხვა ახალ ხაზებს შორის.
- **კატეგორია:** არასავალდებულოა, მერეც შეიძლება არჩევა.
- **რა ხდება შენახვისას:** პროდუქტი იქმნება დამალული (`isActive: false`), ფასით 0, ფოტოს და აღწერის გარეშე, `stock = რაოდენობა − მაღაზიაში`. slug სახელიდან კეთდება. თუ ასეთი slug უკვე არსებობს, ბოლოში კოდი ემატება (`...-sjs-0003`).
- **მაღაზიის ღირებულება:** ახალი პროდუქტის მაღაზიაში გაგზავნილი ნაწილი 0₾-ად ჩაიწერება, რადგან ფასი ჯერ არ აქვს.

**შენახვა** ერთი ტრანზაქციაა: ან ყველაფერი ინახება, ან არაფერი. ორმაგ დაჭერაზე მეორე ჩანაწერი არ იქმნება (`requestKey`, როგორც მაღაზიაში). Enter ფორმას არ ინახავს.

### „აქედან მაღაზიაში“

- **შენახვისას** იქმნება ჩვეულებრივი გადატანა „საწყობი → მაღაზია“, კომენტარით „მიღება #MR-…“ და ბმულით `receiptId`. ის მაღაზიის ჟურნალში, ანალიტიკასა და Excel-ში ჩანს, როგორც ნებისმიერი სხვა გადატანა.
- **ისტორიაში ორი ჩანაწერი:** პროდუქტის მარაგის ისტორიაში ცალ-ცალკე იწერება `+20 Receipt #MR-…` და `−5 Store transfer #ST-…`. ბრუნვითში ეს ჩანს როგორც „მიღება 20, გადატანა 5“.
- **მიბმული გადატანა მხოლოდ თავისი მიღებიდან იცვლება.** მაღაზიის გვერდზე „რედაქტირება“ და „წაშლა“ გამორთულია და ჩანს მინიშნება „მიღება #MR-…-დან, შეცვალე მიღებაში“.
- **მიღების რედაქტირებისას:** თუ მაღაზიის ნაწილი შეიცვალა, გადატანაც იცვლება. თუ ყველა ხაზზე 0 გახდა, გადატანა იშლება. თუ ადრე არ იყო და ახლა გაჩნდა, გადატანა იქმნება.
- **ხელით გადატანა** მაღაზიის გვერდზე ისე რჩება, როგორც ახლაა.
- **არააქტიური მაღაზია:** ველი არ ჩანს.

### ჟურნალი

- **სია:** თარიღი, № (MR-წელი-…), მომწოდებელი, პროდუქტების რაოდენობა, სულ ცალი, აქედან მაღაზიაში, „გახსნა“. დალაგებულია თარიღით, ახლიდან ძველისკენ.
- **ფილტრები:** პერიოდი, მომწოდებელი, პროდუქტი.
- **პროდუქტის ფილტრით** სიის თავზე ჩანს: „სულ მიღებულია N ცალი, M მიღებით, ბოლო: თარიღი“. ეს პასუხობს კითხვას „რამდენჯერ რა მივიღე“.
- **დეტალებში:** ხაზები, დოკუმენტის №, კომენტარი, „დაამატა“ და „შეცვალა“ (email და დრო), მიბმული გადატანის ბმული.
- **Excel:** მიმდინარე ფილტრით. თითო ხაზზე: თარიღი, №, მომწოდებელი, დოკ. №, კოდი, სახელი, რაოდენობა, მაღაზიაში, კომენტარი. ბოლოში ჯამები.

### რედაქტირება და წაშლა

- **რედაქტირება:** ყველა ველი შეიცვლება. მარაგი იცვლება ძველსა და ახალ რაოდენობებს შორის სხვაობით (`Receipt edit #…`), მაღაზიის ნაწილიც იმავე წესით.
- **წაშლა:** ჯერ ჩანს გაფრთხილება „წაიშლება მიღება და მისი გადატანა მაღაზიაში“. მარაგიდან აკლდება `რაოდენობა − მაღაზიაში` (`Receipt deleted #…`), გადატანა უკუიქცევა და ორივე ჩანაწერი იშლება.
- **ნაშთი მინუსში ვერ ჩავა.** თუ საქონელი უკვე გაიყიდა და შემცირება ან წაშლა ნაშთს ნულს ქვემოთ ჩაიყვანდა, მთელი მოქმედება უქმდება, მიზეზის ჩვენებით.
- **ახალი პროდუქტის ხაზი:** მიღების წაშლა მისგან შექმნილ პროდუქტს არ შლის. პროდუქტის მარაგი 0-ზე ბრუნდება და ის დამალული რჩება, საჭიროების შემთხვევაში საწყობიდან წაიშლება.
- **კატალოგიდან წაშლილი პროდუქტი:** ძველი მიღება არ იბლოკება, ხაზი იმავე წესით მუშავდება, როგორც მაღაზიაში. მიღება პროდუქტის სახელსა და კოდს ინახავს, ამიტომ წაშლილის სახელიც ჩანს.
- **სახელი ჟურნალში:** ნაჩვენებია პროდუქტის მიმდინარე სახელი და კოდი. თუ ოთარი გადაარქმევს, ძველ მიღებებშიც ახალი გამოჩნდება.

**✏️ რედაქტირება** ხსნის იმავე ფორმას, რაც დღეს „პროდუქტებშია“: სახელი და აღწერა სამ ენაზე, კოდი, slug, კატეგორია, ფოტოები, ფასი, ფასდაკლება, პრიორიტეტი.
- **მარაგის ველი** იქცევა ტექსტად „მარაგი: N, იცვლება მიღებით ან კორექციით“.
- **„პროდუქტის წაშლა“** ფორმის ბოლოში გადადის, დადასტურებით.

**კორექცია:** ერთი ღილაკი ორი მიმართულებით, „+ მატება“ და „− კლება“. მიზეზი სავალდებულოა, მზა ვარიანტებით: „დათვლის სხვაობა“, „დაზიანება/დანაკარგი“, „სხვა“. ისტორიაში იწერება `Correction: <მიზეზი>`. ფანჯარაში ჩანს მინიშნება: „ახალი ტვირთი „მიღებით“ შეიყვანე“.

**საიტზე ჩართვა.** პროდუქტი ვერ ჩაირთვება, სანამ არ აქვს:
- მინიმუმ 1 ფოტო;
- ფასი > 0;
- კატეგორია;
- ქართული აღწერა.

შემოწმება მუშაობს მხოლოდ გამორთულიდან ჩართვაზე, სიიდანაც და ✏️ ფორმიდანაც. თუ რამე აკლია, ჩანს სია „ვერ ჩაირთო: არ აქვს ფოტო, ფასი“. ამჟამად 51-ვე აქტიური პროდუქტი ყველა პირობას აკმაყოფილებს, ასე რომ ახლანდელ პროდუქტებს ეს არ შეეხება. გამორთვას არაფერი აბრკოლებს.

**ქრება:**
- მენიუს პუნქტი „პროდუქტები“;
- ღილაკი „ახალი პროდუქტი“ (`AddProductDrawer`);
- ძველი გვერდი `ProductManager`.

**მენეჯერი** საწყობს ისევ მხოლოდ ნახვის რეჟიმში ხედავს. ჩართვა, ✏️, კორექცია და წაშლა მისთვის არ ჩანს.

### დამალული პროდუქტის დაცვა საიტზე

მიღებიდან შექმნილი პროდუქტი 0₾-ია. დღეს დამალული პროდუქტი პირდაპირი ბმულით იხსნება, კალათაში ემატება, და საიტის შეკვეთა ამას არ ამოწმებს. ორი ცვლილებით ეს იხურება:

1. **საიტის შეკვეთა** (`createOrder`, ტრანზაქციაში, სადაც პროდუქტი ისედაც იკითხება) უარს ამბობს დამალულ პროდუქტზე: „პროდუქტი აღარ იყიდება“. ადმინის ხელით შეკვეთას ეს არ ეხება, მაღაზიის საქონელი ხელით ისევ გაიყიდება.
2. **დამალული პროდუქტის გვერდზე** მყიდველი ხედავს „პროდუქტი ამჟამად მიუწვდომელია“ და კალათის ღილაკი არ ჩანს.

## 3. ბრუნვითი უწყისი

> **ეტაპი 1 დასრულებულია (22.11):** `classifyStockMovement` ფაილში `src/utils/excelExporter.ts`. რეალურ მონაცემებზე (61 პროდუქტი; ბოლო თვე, 22.08–22.11, მთელი დრო) ფორმულა ყველა პროდუქტზე იხურება, ხოლო „მთელი დროის“ საბოლოო ნაშთი ყველა პროდუქტზე ცოცხალ მარაგს ემთხვევა. 22.08–22.11-ზე ძველი „მიღება“ 259 იყო, ახალი 152 + 107 დაბრუნება. მთელ დროზე „გაყიდვიდან“ კორექციაში გადავიდა 212 ცალი: ხელით „დაზიანება/დანაკარგი“, მათ შორის BLB-0060 −200 (25.06).

სვეტები (Excel, A–K): კოდი, დასახელება, ერთეული, **საწყისი, მიღება, გაყიდვა, შეკვეთებიდან დაბრუნება, გადატანა მაღაზიაში, კორექცია**, ბრუნვის სხვაობა (= საბოლოო − საწყისი), **საბოლოო**.

ფორმულა, რომელიც ყველა პროდუქტზე უნდა ემთხვეოდეს:
`საწყისი + მიღება − გაყიდვა + დაბრუნება − გადატანა + კორექცია = საბოლოო`

მარაგის ისტორიის ჩანაწერები ასე ნაწილდება (რეალურ მონაცემებში მხოლოდ ეს ტიპები გვხვდება):

| ჩანაწერი (`reason`) | სვეტი |
|---|---|
| `Receipt #`, `Receipt edit #`, `Receipt deleted #` | მიღება (ნიშნით; რედაქტირება/წაშლა შეიძლება უარყოფითი იყოს) |
| `Initial stock` (ძველი პროდუქტების შექმნა) | მიღება |
| შეკვეთები: `Order #`, `Order Edit #`, `Order deleted #`, `Order cancelled #`, `Order expired…`, `Rollback (Error)`, `Stock reduction` | კლება → **გაყიდვა**; მატება → **შეკვეთებიდან დაბრუნება** |
| `Store transfer/return …` | გადატანა მაღაზიაში (უცვლელი) |
| `Correction: …` | კორექცია (ორივე ნიშნით) |
| სხვა ხელით ჩაწერილი (ძველი „შევსება“, „დაზიანება/დანაკარგი“…) | მატება → მიღება (როგორც დღეს); კლება → **კორექცია** (დღეს შეცდომით „გაყიდვაშია“) |

- **ძველი პერიოდებიც** ახალი წესით დაითვლება, მიგრაცია საჭირო არ არის.
- **დრო:** მიღება და მისი „აქედან მაღაზიაში“ ნაწილი ბრუნვითში მიღების არჩეული თარიღით ჩანს (ჩანაწერს `effectiveAt` და `receiptId` აქვს; თარიღის შეცვლისას ამ მიღების ძველი ჩანაწერებიც გადადის). საწყისი და საბოლოო ნაშთიც ამ თარიღით ითვლება, ფორმულა იკვრება. ხელით მაღაზიის გადატანა და დანარჩენი ჩანაწერები ისევ შეყვანის დროით ჩანს.
- **Excel და შეტყობინება:** შეჯამების შეტყობინება და Excel ახალ სვეტებს აჩვენებს.

## 4. ტექნიკური დეტალები

- **ახალი კოლექცია `stockReceipts/{id}`:**
  ```
  receiptNumber  "MR-2026-XXXXXXXXXX"
  date           მოძრაობის დღე
  supplier       string
  documentNumber string (შეიძლება ცარიელი)
  note           string
  items[]        { productId, name, productCode, quantity, toStore, createdProduct? }
  totalQuantity, totalToStore
  storeTransferId?          მიბმული გადატანა
  createdAt, createdBy, updatedAt?, updatedBy?, requestKey
  ```
- **მიბმული გადატანა:** `storeTransfers`-ს ემატება `receiptId`, `receiptNumber`. `StoreTransferService.update/remove` უარს ამბობს, თუ `receiptId` აქვს.
- **საერთო მარაგის ფუნქცია:** `applyStockDeltasInTransaction` გადადის საერთო მოდულში (`stockMovements.ts`). ერთ პროდუქტზე ერთ ტრანზაქციაში რამდენიმე ჩანაწერს წერს, თითოს თავისი მიზეზით, რომ „მიღება“ და „გადატანა“ ცალ-ცალკე ჩანდეს. მაღაზიის ქცევა უცვლელი რჩება, რასაც მაღაზიის არსებული ტესტები ამოწმებს.
- **ახალი პროდუქტი** ტრანზაქციაში იწერება `tx.set`-ით. კოდის უნიკალურობა მოწმდება ადმინის real-time პროდუქტების სიით, სანამ ჩაიწერება.
- **Firestore rules:** `stockReceipts`: read/write მხოლოდ `isAdmin()`. ბლოკი გამოქვეყნდება **push-მდე**. პროდუქტის შექმნა ისედაც მხოლოდ ადმინისაა.
- **პროდუქტის რედაქტირება** (`EditProductModalVariants`) `stock`/`totalStock`-ს აღარ აგზავნის.

# 📊 მოგება + AI ბიზნეს-მრჩეველი — საბოლოო გეგმა

> **სტატუსი:** დაგეგმვა დასრულებული · გადახედვის მოლოდინში (გაკეთება ჯერ არ დაწყებულა)
> **თარიღი:** 2026-06-13
> **Stack:** Vite + React 19 + TS SPA · Firebase/Firestore · Vercel `/api/*` serverless (⚠️ **არა** Next.js)

---

## 🎯 ხედვა (ერთ წინადადებად)

AI-მრჩეველი არსებულ შიდა მონაცემზე, რომელიც აჩვენებს **ნამდვილ მოგებას** (შემოსავალი − თვითღირებულება − რეკლამა) და აკეთებს იმ ღრმა ანალიზს, რასაც მენეჯერი ხელით ვერ გააკეთებს — ქართულად, რჩევითა და კითხვა-პასუხით.

## 🚧 რა *არ* არის (ფარგლები)

- ❌ **არა** მარკეტინგ/per-campaign ROAS ხელსაწყო (მხოლოდ blended ხარჯი vs შემოსავალი)
- ❌ **არა** დღის-დონის ტრეკერი (ხელით შეკვეთის თარიღი მიახლოებითია → მხოლოდ coarse/თვიური ანალიზი)
- ❌ **არა** სრული FIFO/WAC საწყობის სააღრიცხვო სისტემა (ნაადრევია — იხ. cost-მოდელი)
- ✅ **არის** სტრატეგიული შიდა მრჩეველი + მოგების ხედი

---

## 🧱 სამი საყრდენი

### 1. პროდუქტის თვითღირებულება (cost)
- `cost` ველი **per-variant** (ვარიანტებს განსხვავებული cost აქვთ; მარტივ პროდუქტს — პროდუქტის დონეზე)
- **გაყიდვის მომენტში `cost` snapshot-დება `OrderItem`-ში** → ისტორიული მოგება ზუსტი რჩება cost-ის შეცვლის შემდეგაც
- **cost დინამიკურია:** მარაგის შევსებაზე მენეჯერი ანახლებს ვარიანტის cost-ს (მიმდინარე/საშ. შესყიდვის ფასი) = **WAC-lite**
- **FIFO/WAC პარტიული აღრიცხვა — განზრახ არა ახლა:** მოითხოვს შესყიდვის-პარტიების ჟურნალს, რომელსაც არა-tech მენეჯერი არათანმიმდევრულად შეავსებს → ნაგავი input. სიზუსტის მოგება მცირეა სტაბილური ფასის პროდუქტებზე. → „მომავალი, თუ მართლა საჭიროა"

### 2. რეკლამის ხარჯი (adSpend)
- **ფაზა A — ხელით:** ახალი კოლექცია `adSpend`, ჩანაწერი `{ კვირა/თარიღი, თანხა }`. **მინ. კვირეული რეზოლუცია** (თვიური პროაქტიულ AI-ს კლავს)
- **ფაზა B — Meta API:** serverless `/api/meta-spend` იღებს **ანგარიშის საერთო ხარჯს თარიღებით** (Pixel **არ** სჭირდება — Pixel მხოლოდ per-sale attribution-ისთვისაა, რასაც არ ვაკეთებთ). ერთჯერადი auth-setup, მერე ავტომატური

### 3. AI ფენა
- მთლიანად **serverless** `/api/ai-advisor` — Gemini API key **server-side**, არასდროს client-ში
- **მოდელი:** მიმდინარე საუკეთესო **Flash** (იაფი/სწრაფი; „1.5" მოძველებულია). ღრმა სტრატეგიულ რეჟიმზე Pro = ვარიანტი, თუ ხარისხი გაამართლებს
- **პრინციპი:** კოდი ითვლის ციფრებს (ზუსტად) → AI კითხულობს/ხსნის/ურჩევს. **AI თანხას არ იგონებს**

## 🧮 მოგების ფორმულა

```
წმინდა მოგება (პერიოდი) =
    შემოსავალი        (მხოლოდ მიტანილი/delivered შეკვეთები)
  − საქონლის ხარჯი    (Σ რაოდენობა × snapshot cost)
  − რეკლამა           (პერიოდის adSpend ჯამი)
  − მიწოდება          (მხოლოდ თუ ბიზნესი იხდის — toggle)
```

**წესები:**
- **მხოლოდ delivered** — „გზაში" მყოფი = პოტენციური; გაუქმებაზე უკუსვლა AI-ს არევდა
- **მიწოდება = კონფიგურირებადი toggle** — pass-through (კლიენტი→კურიერი, ნული) vs OPEX (უფასო მიწოდება = ხარჯი)
- **გაუქმებული** — შემოსავალში არა, მაგრამ adSpend მაინც დაიხარჯა (sunk)
- **ისტორია = zero-day policy** — ზუსტი მოგება ფუნქციის ჩართვის დღიდან. (არჩევით: აშკარად ნიშანდებული „მიახლოებითი" ისტორიული ტრენდი, თუ მფლობელს უნდა)

## 📈 რას ითვლის კოდი (AI-ს მიეწოდება — „ანალიტიკური პროფილი")

ყველა **თარიღ-მდგრადია** (თვის/არა-დღის დონე):

| ჯგუფი | მეტრიკა |
|---|---|
| მოგება | შემოსავალი / COGS / რეკლამა / წმინდა / მარჟა % |
| მოგება ჭრილებში | პროდუქტი/კატეგორია — *ნამდვილი მოგება*, არა ბრუნვა |
| ხაფანგი | მაღალი ბრუნვა + დაბალი მარჟა |
| ზრდა | წინა პერიოდთან (უკვე გვაქვს) |
| Retention | განმეორების %, თვიური კოჰორტა |
| Churn | ღირებული + 60+ დღე გაჩუმებული — სია |
| Affinity | რა იყიდება ერთად (cross-sell) |
| მარაგი | სიჩქარე, „X დღეში გათავდება", reorder |
| არხები | შემოსავალი/მარჟა/განმეორება წყაროზე |

## 🏗️ არქიტექტურა (ფონური კალკულაცია)

**ახლა: on-demand client-side + thin serverless proxy. Cron/Cloud Functions — არა.**

```
1. Client ითვლის "ანალიტიკურ პროფილს" (არსებული ლოგიკის reuse;
   ყველა შეკვეთა ისედაც client-ში აქვს ჩატვირთული)
2. აგზავნის კომპაქტურ მეტრიკებს → /api/ai-advisor (Vercel serverless)
3. ფუნქცია უმატებს Gemini key-ს (server-side) → Gemini → პასუხი
```

- 285 (→1000) შეკვეთაზე ეს კალკულაცია = მილიწამები. Cron ზედმეტია
- **Scheduled aggregation (Cloud Functions/Cron + daily summary docs) — მერე**, როცა: მოცულობა გაიზრდება (ათასობით, reads-ის პრობლემა) ან proactive digest user-ის გარეშე დაგვჭირდება
- იგივე „გადავდოთ სანამ საჭიროა" პრინციპი, რაც Firestore reads-ზე შევთანხმდით
